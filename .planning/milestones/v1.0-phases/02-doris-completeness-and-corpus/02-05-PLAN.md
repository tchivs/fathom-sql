<context>
The research sketch (Code Example 12) and pattern map define the analyzer shape: ColumnInfo { name, data_type }, TableInfo { name, columns }, trait Catalog { table(name) -> TableInfo? }, and StaticCatalog backed by a Map, with analyzer/moon.pkg importing only syntax (never parser). The parser package today imports exactly source, token, lexer, syntax (parser/moon.pkg) — that import list is the boundary contract (D-21). The name-resolution demo resolves table references from syntax read views for the DML/DDL kinds shipped in 02-01/02-02 (Statement wrapper containing Insert/Update/Delete/Merge/CreateTable). ParseResult already carries statement_id on every PrimitiveDiagnostic and one Statement node per segment (root.children index == statement order); D-23 adds explicit accessors. This plan deliberately does NOT touch parser.mbt, token.mbt, or syntax.mbt — only api.mbt gains additive accessors, keeping the core grammar stable while the analyzer lands alongside (add-alongside decision above).
</context>

## Trust Boundaries
| Boundary | Description |
|---|---|
| Caller-provided Catalog → analyzer | Catalog metadata is untrusted caller data; it must never reach the parser or the syntax-only valid channel. |
| Parser package → analyzer | A stray import would couple syntax parsing to catalog semantics. |
| statement_id → accessors | Mis-mapping ids would mislocalize diagnostics for consumers. |
